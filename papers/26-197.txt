Subject: Fixing Deferred Kind and Rank Equivalence

1. Background
==============

When introducing templates, some way of determining whether two
entities have the same rank or kind was needed in the case the rank
or kind depends on a deferred constant. The current wording uses
the term "syntactically equivalent." The editor points out this
term is not defined, and is likely not the correct term to use.

Additionally, an entity declared to have the same rank as a deferred
rank entity is explicitly said to have the same rank, but the same
is not true of deferred kind. This is inconsistent.


2. Design
=========

We still need some way of saying whether two expressions depending on
one or more deferred constants are the same, in order to be able to
say whether two entities whose rank or kind depend on those
expressions have the same rank and kind. A new term is introduced
with a definition that allows expressions that are instantiation
associated to be considered the same, but that does not require a
processor to perform algebraic manipulations to solve the general
case of whether two expresssions are equivalent.

Additionally, we expand the definition of when two entities have the
same deferred-kind type parameter value to include the case of one
entity's kind type parameter being declared as a reference to the
other entity's kind type parameter, analogous to how it is already
done for deferred rank with RANK (RANK (x)). Such a reference can be
written either as the argument of the intrinsic function KIND or as a
type-param-inquiry (e.g. x%k) accessing a named kind type parameter of
a derived-type entity, so that this also covers derived types with
multiple kind type parameters.

[130:1-] Immediately before 8.5.9 EXTERNAL attribute, insert new NOTE

    "NOTE 3

    In the following example, the REQUIREMENT rank_example declares a
    deferred interface whose dummy argument x has deferred rank
    RANK(n). The TEMPLATE outer associates its own deferred constant
    sz with rank_example's deferred argument n via the REQUIRE
    statement. Because n and sz are associated by instantiation
    association, "n" and "sz" are the same deferred constant
    expressions, so x and y have the same rank, and the call to impl is
    valid without requiring assumed-shape argument association.

    REQUIREMENT rank_example {n, proc}
        DEFERRED INTEGER, PARAMETER :: n
        DEFERRED INTERFACE
            SUBROUTINE proc (x)
                INTEGER, RANK (n) :: x
            END SUBROUTINE
        END INTERFACE
    END REQUIREMENT

    TEMPLATE outer {sz, impl}
        DEFERRED INTEGER, PARAMETER :: sz
        REQUIRE rank_example {sz, impl}
    CONTAINS
        SUBROUTINE wrapper (y)
            INTEGER, RANK (sz) :: y
            CALL impl (y) ! valid, rank expressions are the same
                          ! deferred constant expression
        END SUBROUTINE
    END TEMPLATE

    The same rule applies when the instantiation argument is a more
    complex expression: had the REQUIRE statement instead been
    REQUIRE rank_example {sz+1, impl}, then "n" and "sz+1" would be
    the same deferred constant expressions, so a dummy argument
    declared RANK(sz+1) in outer would have the same rank as x."
